## 2.2.3 اختبار الانحدار المؤتمت باستخدام GenAI

مع الإصدارات المتكررة يزيد حجم اختبارات **Regression**. تكرار تشغيلها في CI/CD يجعل الأتمتة مفيدة، ويمكن لـGenAI دعم إنشاء السكربتات وصيانتها وتحليل أثر التغييرات. الدعم يشمل الاختبارات الوظيفية وغير الوظيفية، لكنه لا يبرر تشغيل كود غير مُراجع.

| الاستخدام | كيف يساعد؟ | ما الذي نتحقق منه؟ |
|---|---|---|
| Keyword-driven scripts | تحويل خطوات إلى كلمات مفتاحية موثقة | وجود الكلمات وتواقيعها وترتيبها |
| Impact analysis | اقتراح المناطق المتأثرة بتعديل الكود | اعتماديات لم تظهر في المدخلات |
| Self-healing | تكييف محددات أو تفاعلات تغيرت | أن الإصلاح لا يخفي عيبًا فعليًا |
| Reporting | تلخيص النجاح والفشل والاتجاهات | الحسابات ومصدر كل نتيجة |
| Defect reporting / RCA | جمع السجلات والصور والبيئة واقتراح أسباب | فصل السبب المثبت عن الفرضية |

اختبارات GUI تتأثر بالمحددات الديناميكية والتغيرات البصرية والتفاعلات. اختبارات API تتأثر بالمسارات وبنية الطلب والاستجابة والمصادقة؛ يجب تزويد النموذج بالمواصفات المعتمدة كي لا «يصلح» الاختبار بطريقة تتسامح مع انحراف غير مقصود في العقد.

### إنشاء وتصحيح سكربت بالكلمات المفتاحية — HO-2.2.3a

هذا إطار تدريبي افتراضي، وليس مكتبة جاهزة للتثبيت:

| الكلمة | الوسائط | السلوك الموثق |
|---|---|---|
| OpenRegistration | لا شيء | يفتح شاشة التسجيل |
| FillEmail | بريد | يعبئ البريد |
| FillPassword | كلمة مرور | يعبئ كلمة المرور |
| SubmitRegistration | لا شيء | يرسل النموذج |
| ExpectAccountCreated | لا شيء | يتحقق من إنشاء الحساب |
| ExpectNoAccount | لا شيء | يتحقق من عدم إنشاء حساب جديد |

أعط النموذج مثال تسجيل صحيح ومثال بريد فارغ باستخدام هذه الكلمات. اطلب إنشاء حالة كلمة مرور من 11 محرفًا، مع القيد «استخدم المكتبة الموثقة فقط». راجع المسودة ثم افحصها بالأداة الفعلية في بيئة اختبار عندما تربطها بإطارك.

```text
OpenRegistration
FillEmail learner01@example.test
FillPassword abcdefghijk
SubmitRegistration
ExpectNoAccount
```

هذا تسلسل توضيحي لا نتيجة تشغيل حقيقية. يحتاج اختبار المنتج الفعلي إلى تأكيد رسالة الخطأ المناسبة أيضًا وفق المتطلب ومكتبة الكلمات المتاحة. إن اقترح النموذج كلمة غير موثقة، لا تضفها سرًا للمكتبة؛ صحّح الطلب أو حدّث المكتبة بمراجعة واضحة.

في مرحلة التصحيح استخدم توجيه نظام يحدد دور المساعد وحدود المكتبة، ثم مرّر السكربت وسجل الفشل. اطلب تحديد الخطوة المخالفة وإصلاحها وتفسيرًا موجزًا يستند إلى السجل. قارن قبل/بعد وأعد التشغيل، ثم وسّع التغطية بحالات إضافية.

### تحليل تقرير الانحدار — HO-2.2.3b

بيانات افتراضية: TC-01 فشل برسالة locator missing، وTC-02 فشل بـHTTP 500، وTC-03 تخطّاه المشغّل. لدى الفريق عيب معروف KB-7 عن محدد قديم في شاشة التسجيل.

سلسلة العمل: قارن النتائج بمواصفة الاختبارات أولًا؛ ثم اجمع الأعراض المتشابهة؛ ثم قارن بمسجل العيوب المعروفة؛ ثم أعد فحص الأدلة. المخرج المناسب يربط كل ملاحظة بمعرّف الحالة والسجل وحالة الفرضية.

النتيجة التعليمية: TC-01 قد يرتبط بـKB-7 بعد فحص الإصدار والخطوة؛ TC-02 يحتاج تحقيقًا مستقلًا ولا يكفي HTTP 500 لتسمية سبب جذري؛ TC-03 غير منفّذ وليس نجاحًا. احتفظ بقائمة الشذوذ المعروفة وأسباب الاستبعاد حتى لا تضيع الحالات عند التلخيص.

<details><summary>تغيّر زر «إرسال» فاختار Self-healing زر «حذف». هل نجاح التنفيذ مقبول؟</summary><p>لا. تطابق المحدد أو قابلية النقر لا يثبتان المعنى الصحيح. تُراجع نية الخطوة والنتيجة المتوقعة، وقد يلزم رفض الإصلاح وإحالة الحالة لمختبر.</p></details>
